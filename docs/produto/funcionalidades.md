# Funcionalidades do Clipes: o que o núcleo faz e o que a UI precisa mostrar

Este documento é a base do front v2. Ele lista **todos os 237 comandos do núcleo** (as "rotas" do app), agrupados pela jornada do usuário, com entrada, saída, erros, eventos, pré-condições, a tela que usa cada um hoje e as histórias de usuário do #26 que o justificam. Nada aqui propõe telas: é o inventário do que existe, para o redesenho partir de fatos.

Gerado a partir do `master` em `d90ec85` (17/11/2026). A lista de comandos saiu do código (`CommandRegistration` em `core/src/**`) e foi conferida contra o mock TS e as telas.

## Como o app funciona, para quem pensa a partir do backend

O Clipes é um app **Tauri**. Na prática, são duas peças no mesmo processo:

- **A janela** é uma WebView (um navegador embutido) que roda o React de `src/`. É o "front".
- **O núcleo** é a crate Rust `core/`. É o "backend". Não há servidor HTTP entre os dois.

A UI fala com o núcleo por **um único comando Tauri**, `core_dispatch(nome, json)` (`src-tauri/src/main.rs`). O `nome` é a "rota" (`projects.open`, `transcription.start`, `editor.undo`...), e o `json` são os argumentos. O núcleo procura o comando registrado com aquele nome e devolve um JSON de resposta ou um erro `CoreError { code, message, usage? }`. Pense em `core_dispatch` como um único endpoint `POST /rpc` com o nome do método no corpo. No front, a chamada é `coreDispatch<T>(nome, args)` em `src/lib/core.ts`.

Coisas que demoram (transcrever, exportar, chamar a IA) viram **jobs**: o comando enfileira o trabalho e responde na hora com o id do job. O progresso chega depois, pelo **evento** Tauri `core-progress` (pense num WebSocket de mão única), com `{ job, project?, stage, percentage, message, error? }`. A UI escuta esse evento e pergunta o estado final com o comando `*.status` do domínio. A fila de jobs vive no SQLite do Projeto, então sobrevive a o app fechar: ao reabrir, jobs locais voltam para a fila e jobs pagos ficam "incertos" até o usuário decidir (ver [07](funcionalidades/07-provedores-jobs-e-eventos.md#a-fila-de-jobs-coresrcjobsrs-e-coresrcjobs)).

Duas peças auxiliares:

- **Worker Python**: processo separado, instalado sob demanda, que faz a Transcrição local (Whisper/VAD). O núcleo conversa com ele; a UI nunca fala com ele direto.
- **Mídia**: a UI não lê arquivos do disco. Ela toca vídeo e áudio por URL: o protocolo `clipes-media://` no Windows/macOS, ou um HTTP de loopback com token no Linux (comando Tauri `media_base_url`, ADR-0004). O recurso é um id opaco, nunca um caminho.

Para rodar a UI sem Rust existe um **núcleo de mentira em TypeScript** (`VITE_CORE_MOCK=1`, `src/lib/core.ts` e `src/lib/*Mock.ts`). O `bun run test:ui` (Playwright) usa ele. Hoje o mock cobre 206 dos 237 comandos, e vários só respondem com flags na URL (`?source-test`, `?transcript-test`).

## O que o inventário mostrou

### Números

- **237 comandos** registrados; os 237 estão documentados (nenhum faltando, nenhum duplicado).
- **28 comandos sem chamada em tela**: 19 não aparecem nem na UI nem no mock; 9 só aparecem no mock. Lista em [Comandos sem tela](#comandos-sem-tela).
- **12 comandos** chamados pelas telas **sem cobertura no mock**, entre eles `projects.create`, `projects.open`, `components.settings.set` e `backups.create`. Para o front novo rodar inteiro no navegador, o mock precisa crescer.
- **5 páginas** hoje: Projetos (51 linhas no topo, mais uma árvore de ~6.400 linhas que concentra quase tudo), Componentes, Preferências, Sobre e Relatos. O editor abre por cima, como overlay.

### Problemas de UX da UI atual (detalhes e arquivo:linha no [apêndice](funcionalidades/90-inventario-ui-atual.md#problemas-de-ux-observados))

1. **Scroll sem fim**: Projetos → Fontes → Transcrição → Seleção → Revisão ficam aninhados numa única página.
2. **Coluna única estreita** (`max-w-4xl`) em todas as páginas, centralizada.
3. **Navegação por `useState`**, sem URL, sem etapas, sem voltar.
4. **Faltam estados** de carregamento e vazio em várias telas.
5. **Erros técnicos crus** na tela; quase todos os `CoreError` tipados viram mensagem genérica.
6. **Ações destrutivas** sem confirmação, ou com `window.confirm`.
7. **Foco e teclado**: `tabIndex=-1` em elemento interativo, trap de foco incompleto, atalhos `[` e `]` em conflito entre a revisão e o shell.

### Coisas que o front novo precisa saber sobre o contrato

- **Dois jeitos de cancelar**: `jobs.cancel` (fila do Projeto, id numérico) e `components.cancel` / `tts.models.cancel` (downloads globais, id em texto). Alguns domínios ainda têm job síncrono com nome em texto.
- **`snake_case` e `camelCase` misturados** nos payloads (ex.: `export.*` e `thumbnail.*` em snake; `script.*`, `narration.*`, `packaging.*` em camel; `jobs.preview` exige `source_id`). Há três estilos de paginação na Transcrição.
- **O campo `project`** é obrigatório em alguns comandos e redundante em outros (o núcleo já sabe qual Projeto está aberto).
- **Desfazer/refazer**: o editor tem pilha por Corte; as correções de Transcrição têm uma pilha só para o Projeto inteiro. `editor.crop.set_suggested` e `editor.crop.example` não entram no desfazer. `editor.snapshots` existe, mas não há comando para restaurar um snapshot.
- **Funcionalidades prontas no núcleo e sem tela**: auditoria de chamadas de IA (`provider.audit.list`), leitura do orçamento (`jobs.budget.get`), refazer job de IA com outro perfil (`jobs.redo`), histórico de revisões da seleção (`selection.get { revision }`), faixas de duração customizadas na seleção (`minUs`/`maxUs`), palavras e frases da Transcrição.
- **Funcionalidades que não existem no núcleo**: excluir uma Fonte; cookies e download por trecho na importação por URL (há pesquisa em `docs/research/`, sem implementação).
- **Mudar a pasta de dados** (`components.settings.set`) redireciona componentes e modelos, mas não move o que já foi baixado nem os arquivos globais (`projects.json`, `export-encoder.json`, `diagnostic.log`).

### Bug encontrado na v1

`export.status` lê `encoder`, `fallback_from` e `fallback_reason` do SQLite (`core/src/export.rs:1125`) mas não os devolve no JSON (`core/src/export.rs:1138`). A tela espera `encoder_fallback` (`src/features/export/ExportButton.tsx:190`), então o aviso "a exportação caiu para a CPU" só aparece no mock, nunca no app real.

## Comandos sem tela

Sem uso na UI **e** sem mock (19): `documents.validate`, `editor.snapshots`, `energy.start`, `jobs.budget.get`, `jobs.preview`, `jobs.redo`, `jobs.redo.estimate`, `jobs.result`, `projects.close`, `provider.audit.list`, `provider.capabilities`, `provider.cost.run`, `provider.structured`, `proxy.map_time`, `script.narration_allowed`, `transcription.blocks`, `transcription.hardware.diagnostic`, `transcription.sentences`, `transcription.words`.

Só no mock, sem chamada direta em tela (9): `batches.get`, `editor.range`, `editor.crop.get`, `editor.crop.evaluate`, `editor.crop.example`, `editor.montage.get`, `captions.overrides`, `captions.style.get`, `export.batch.status`. Alguns chegam à tela por dentro de outra resposta (ex.: o estado do crop vem junto de `editor.open`).

Parte desses comandos é de uso interno ou do harness de agentes (`provider.structured`, `provider.capabilities`, `documents.validate`); os verbetes dizem qual é qual.
